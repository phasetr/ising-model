# Issue #4721: build-speed: replace cast-positivity with Nat.cast_nonneg at the two FV ratio modules (A/B measured -3.75s)

**Status**: OPEN

**Created**: 2026-07-25/26 (`dev-perf` A/B measurement)

GitHub: https://github.com/phasetr/ising-model/issues/4721

## Summary

`dev-perf` measured (A/B, own-cost = real − import, median of 3, warm, serial, on a `$TMPDIR`
copy; repo left unmodified during measurement) that 5 `by positivity` call sites across 2 files
are interpreted-`positivity` hot spots and should be replaced with an explicit
`Nat.cast_nonneg _` term.

## Measured (base = current `by positivity`, explicit = proposed replacement)

| File | Sites | base own-cost | explicit own-cost | reduction |
|---|---|---|---|---|
| `IsingModel/Concrete/LatticeGraphCorrelation/Lemma_17_5_2/MassContinuityFiniteVolumeDartRatio.lean:95` | `by positivity` ×3 | 3.73s | 1.61s | −2.12s (−57%) |
| `IsingModel/Concrete/LatticeGraphCorrelation/Lemma_17_5_2/MassContinuityFiniteVolumeIncidentRatio.lean:80` | `by positivity` ×2 | 3.25s | 1.63s | −1.62s (−50%) |
| **Total** | 5 sites | | | **−3.75s** |

Line 95 of `MassContinuityFiniteVolumeDartRatio.lean` was originally estimated at 2 `positivity`
calls; the actual count is **3** (all three sit on the same line; the third was below the
profiler's 100ms display threshold and was invisible until per-file profiling).

## What the goals actually are

All 5 sites are arguments to `pseudoMassG_ratio_le`'s `(ha : 0 ≤ a) (hb : 0 ≤ b) (hc : 0 ≤ c)`
(and the 2-argument sibling `pseudoMassG_single_ratio_le`), and in every case the goal reduces to
`0 ≤ ((latticeDistance d _ _ : ℕ) : ℝ)` — plain ℕ→ℝ cast non-negativity. `Nat.cast_nonneg _`
closes each goal directly; no context-dependent hypothesis is needed.

## Proposed replacement (verified to compile, warning-free, under 100 columns)

```lean
    (c := (latticeDistance d x y : ℝ)) hm_nn (Nat.cast_nonneg _) (Nat.cast_nonneg _)
    (Nat.cast_nonneg _) hexp
```

(analogous 2-argument form for `MassContinuityFiniteVolumeIncidentRatio.lean:80`).

## Notable findings (record verbatim, do not re-derive)

- The explicit-term replacement is even faster than a `by sorry` stub at the same site (base
  3.73s / stub 1.64s / explicit 1.61s for the DartRatio file), so the fix recovers essentially
  **100%** of the available interpreted-tactic cost, not merely a partial reduction.
- Two sibling (non-FV) files with the textually identical `positivity` pattern were also measured
  and are **out of scope** because their own-cost is negligible:
  - `MassContinuityDartSum.lean:96` (×3 `positivity`): −0.12s (within noise).
  - `MassContinuityIncidentRatio.lean:120` (×2 `positivity`): 0s difference.
- No shared lemma/helper is warranted: the goal is exactly mathlib's `Nat.cast_nonneg`.
- **General finding**: interpreted `positivity` can cost 10× more in one file than in another
  file with a textually identical call, so "positivity is present → it's slow" is not a valid
  heuristic. Any future build-speed pass must profile per-file
  (`lake env lean -Dprofiler=true`, ≥100ms threshold) before assuming a `positivity` call is a
  hot spot.

`0 ≤ (↑(_ : ℕ) : ℝ)` should use `Nat.cast_nonneg` instead of `positivity`. Per `skill-curation`,
any such skill-text change must go through `skills/skill-curation/inbox.md` first, not a direct
