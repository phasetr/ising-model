# #4519: [benchmark] Measure incremental build impact of R1/R2/R5

**State**: CLOSED (NOT_PLANNED)
**Closed At**: 2026-07-15T12:14:13Z

## Objective

Measure whether the completed R1/R2/R5 refactors reduced incremental build time by at least 10%, as required by tracker #4506. This issue is measurement-only: do not change Lean source, imports, proofs, module layout, or documentation claims to improve the result.

## Compared revisions

- **Before**: `6a2470114fe0b5dd5c6cdcbb0e02b8acca351fb4` — the clean commit immediately before R1 batch 1 and therefore before R1, R5, and R2.
- **After**: `94ceb4f83906dc23069b7566ce31242240e22855` — authoritative current main after R1, R5, R2, R3 restoration, and #4517 documentation synchronization.
- Record intervening R1/R5/R2 commits `86bed7d8`, `9f139d2a`, `c931cdee`, and `8134e835` in the report. Do not attribute every observed delta to one refactor without a separate experiment.

## Isolation and reproducibility

- Use two separate, clean detached worktrees at the exact before/after SHAs. Both worktrees must remain tracked-clean before and after every scenario.
- Use worktree-local build artifacts and logs; do not share mutable IsingModel `.olean` outputs between revisions.
- Use the same machine, power state, shell, filesystem, and measurement tool. Record CPU/model, RAM, macOS version, Lean/Lake versions, `lean-toolchain`, `lake-manifest.json` hash, and relevant environment variables.
- Prepare equivalent dependency caches for both worktrees. Do not include dependency download/network time. If toolchain or dependency locks differ, disclose this and do not claim refactor-only causality without normalization.
- Ensure no concurrent `lake`/`lean` process or other known heavy workload. Record load average and thermal/power conditions.
- Alternate before/after run order to reduce drift. Do not discard runs except for a documented invalidation reason.
- Preserve raw commands, stdout/stderr, `/usr/bin/time -l` output, artifact snapshots, and a machine-readable CSV/TSV under gitignored `.self-local/`.

## Predeclared scenarios

Run each scenario independently for both revisions.

1. **Cold full build** — 3 valid repetitions. Start from equivalent dependency-prepared worktrees with all project-local IsingModel build artifacts absent, then build `IsingModel`.
2. **Warm no-op full build** — 5 valid repetitions. Immediately rebuild `IsingModel` without source or artifact changes; rebuilt IsingModel `.olean` count should be zero.
3. **Hub-touch incremental build** — 5 valid repetitions. From a warm state, update only the mtime of the common hub `IsingModel/Concrete/LatticeGraphCorrelation/PerStageComplex.lean`, then build `IsingModel`. Restore a clean tracked state after every run.
4. **Leaf-target build** — 5 valid repetitions. Measure the common logical target `IsingModel.Concrete.LatticeGraphCorrelation.PerStageComplex.Bounds.PolynomialLower` from an equivalent prepared state. Record that this path changed from a pre-R2 compatibility/aggregation role to a retained consolidated content module.

If a command cannot express the intended scenario identically at both revisions, stop and amend the protocol in the issue before collecting result-bearing runs; do not silently substitute different workloads.

## Metrics for every repetition

- wall-clock time
- user CPU time
- system CPU time
- maximum resident set size, with units
- exit status and warning count
- number and list of rebuilt IsingModel `.olean` files, determined from pre/post artifact snapshots rather than terminal job counts alone
- total IsingModel `.olean` count and bytes after the run
- scenario, revision, repetition number, run order, start time, load average, and invalidation reason if any

Use the median of valid repetitions as the reported central value for every metric. Also report min/max and individual raw values; do not report only the best run.

## Primary acceptance threshold

The tracker’s quantitative criterion is evaluated on the predeclared **hub-touch incremental build median wall time**:

```
improvement_percent =
  100 * (before_median_wall - after_median_wall) / before_median_wall
```

- **PASS**: improvement is at least 10%.
- **FAIL**: improvement is below 10% or the after median regresses.
- Cold, warm, and leaf-target results are required diagnostics but do not replace or override the primary metric.
- Report user time, RSS, and rebuilt-`.olean` deltas even when wall time passes. Explain any material regression (greater than 10%) in a secondary metric.
- Do not change the threshold, scenario, target, repetition count, or exclusion rules after seeing results.
