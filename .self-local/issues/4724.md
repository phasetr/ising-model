# Issue #4724: build-speed: reconcile the 4.5x discrepancy between the two per-module fixed-cost measurements before resuming #4563

**Status**: OPEN

**Created**: 2026-07-26 (filed via `dev-pr-clerk`)

GitHub: https://github.com/phasetr/ising-model/issues/4724

## Summary

This is a **numeric discrepancy**, not a directional disagreement. Both #4563 and the
full-coverage `dev-perf` measurement agree on **direction**: consolidating
`AmbientLattice/SpecialCases` per-theorem modules back into fewer parent modules is expected to
reduce build cost (#4563's own title/objective is "Re-merge … per-theorem module splits" /
"Consolidate … to reduce import overhead"; the pilot merges 10 `Magnetization*` modules into 1
parent umbrella). What is unresolved is **how large that effect actually is**, because two
measurements of the same underlying quantity (per-module fixed build cost) disagree by roughly
**4.5x**.

## The two measurements

- **Measurement A (2026-07-18, decision basis for #4563)**: single-process per-module timing
  methodology (precedent #4533/#4521), applied to the `Magnetization*` pilot family (10 modules,
  ~65s CPU → ~6.5s wall). Reported as **per-module fixed cost ≈7.0s**, yielding "10.5x median
  (9.3x mean) fixed-cost per-module import overhead" reduction for the pilot consolidation
  (issue #4562 resolution comment; carried into #4563's decision gate).
- **Measurement B (2026-07-24/25, full-coverage `dev-perf` sweep)**:
  `.self-local/reports/perf-full-coverage-buildtime-4b14a205.md`, "Scale check" section — a clean
  full build of all **2011** modules, library user-CPU = 4031s (mean **~2.0s/module** own-cost).
  The same report separately measures serial `import` cost at **1.55–2.19s/module (mean ~1.8s)**,
  i.e. of the same order as own-cost. This is a full-coverage measurement (every module in the
  library), not a single-family pilot.

**A / B ≈ 7.0 / 1.8 ≈ 3.9x** using B's mean (~1.8s/module), and **≈3.2–4.5x** across B's measured
range (1.55–2.19s/module) against A's 7.0s. Under measurement A, an 8-to-1 consolidation is worth
tens of seconds; under measurement B, the same consolidation is worth roughly an order of
magnitude less. The expected payoff of #4563's next candidate family
(`SusceptibilityPointwiseRegularity*`, 8 modules) therefore swings from **~10s to ~49s CPU
(≈1–5s wall)** depending on which measurement is trusted — already recorded in #4563's own
"2026-07-25 status" section as the reason a fresh measurement is required before that family is
attempted.

## This issue does not contradict #4563's own status section

#4563 already added a "2026-07-25 status" section (dev-pr-clerk) that states the A/B disagreement
and requires a `dev-perf` before/after re-measurement before implementation resumes, even under
standing authorization. This issue exists to track that reconciliation as an **independent,
closeable item** (so it is not buried inside #4563's authorization-gate discussion), and records
no new conclusion beyond what #4563 already states.

## Proposed reconciliation measurements (not yet authorized — record only)

1. **Re-measure under one shared protocol.** Measurement A and B most likely differ because their
   protocols differ (A: single-process per-module timing on a 10-module pilot; B: full clean
   `lake build` divided by module count, serial `import` extracted separately). Re-run both
   protocols against the *same* module set and reconcile `real − import` definitions before
   trusting either number for a specific family's payoff.
2. **Direct consolidation A/B experiment.** Actually merge a small family (e.g. the already-vetted
   `Magnetization*` pilot, or the `SusceptibilityPointwiseRegularity*` candidate) in a disposable
   worktree, run `lake clean && lake build` before/after, and compare wall-clock and user-CPU
   directly — this sidesteps the per-module-fixed-cost abstraction entirely. Must be done in a
   separate worktree so the main tree's warm `.lake` cache is not disturbed.
3. **Structural driver, left unmeasured.** Measurement B's report explicitly flags, as a caveat
   and not a measured conclusion, that "module *count* — not any tactic — is the dominant
   structural cost driver" for this library at its current scale (2011 modules), while also
   noting the parallel build's page-cache effects make this an upper bound. This structural claim
   is recorded here as unmeasured/untested, not as a finding to act on.

## Recommendation

Before resuming #4563's family-by-family consolidation (28 families remaining), reconcile this
numeric discrepancy so the expected payoff per family can be estimated to within less than the
4.5x current spread. This is consistent with — not in addition to — the re-measurement #4563's
own "2026-07-25 status" section already requires; it does not ask to park #4563.
